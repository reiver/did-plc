DID-PLC

the most popular DID used by ATProto

by Charles Iliya Krempeaux

What is DID-PLC‽

If you have used Bluesky, or Blacksky, or Leaflet or anything else built on ATProto (the Authenticated Transfer Protocol), then you have probably seen something like this:

That is a DID-PLC. (This particular one belongs to the account with the handle @atproto.com.)

The most succinct way I can think of to explain what a DID-PLC is is:

🠶 a permanent identifier for an account, whose “code” is (the first part of) a hash of the account's first signed operation

But that lacks context. What is a DID? What is an “operation”? What exactly gets hashed, and how? And, where do these things live?

This article answers those questions. It is written for programmers who want to create ATProto apps. And, after reading it, you should:

  • understand what the code (i.e., what is after the did:plc:) of a DID-PLC is,
  • be able to write a program that generates that code,
  • be able to get information from plc.directory,
  • and, be able to add a new DID-PLC to plc.directory.

The programming examples are in the Go programming-language (Golang). And, they only use Go's standard library.

DID-PLC is also written as did:plc. And, PLC stands for Public Ledger of Credentials.

DID

Before we can talk about DID-PLC, we need to talk about DIDs.

DID is short for Decentralized Identifier. DIDs are a W3C standard. Decentralized Identifiers (DIDs) v1.0 became a W3C Recommendation on 19 July 2022.

A DID is a type of URI. It always starts with did:. After that comes the name of a DID method. And, after that comes an identifier, whose format is decided by that DID method.

There are many DID methods. For example: did:web, did:key, did:plc, and many more.

A DID by itself is just a name. What makes it useful is that it can be resolved to a DID document — a JSON document that says things about the thing that the DID identifies. Such as: what public-keys it uses, what other names it is known by, and what services it uses.

Each DID method has its own way of resolving a DID into a DID document. For example, did:web uses HTTPS and DNS. And, did:plc uses a directory server (such as plc.directory).

(DIDs are designed to be permanent identifiers. Things you might think of as an “identity” — such as a handle, a server, or a key — can change. The DID stays the same.)

DIDs in ATProto

In ATProto, every account is identified by a DID. Your handle (such as @atproto.com or @alice.bsky.social) can change. The server that hosts your data (your PDS, short for Personal Data Server) can change. Your DID does not change.

ATProto currently supports two DID methods:

  • did:plc
  • did:web

Almost all ATProto accounts use did:plc. As of this writing, more-than 40 million did:plc identifiers have been registered.

For ATProto, a DID document tells you 3 important things about an account:

handle

found in alsoKnownAs, as an at:// URI. For example, at://atproto.com.

signing-key

found in verificationMethod, with an id ending in #atproto. This is the public-key used to verify the account's data (its repository).

PDS

found in service, with an id ending in #atproto_pds. This is the URL of the server that hosts the account's data.

The Code

So, what is the code‽ Where do those 24 characters come from?

That is a mouthful. So, let's go through it, piece by piece.

Every DID-PLC has a log of operations. An operation is a small (signed) JSON object that says what the handle, keys, and services of the account are. Every time one of those changes, a new operation is added to the log.

The very first operation in the log is called the genesis operation. And, the DID-PLC is made from it. Like this:

The SHA-256 hash is 256 bits. Its base32 encoding is 52 characters. But only the first 24 characters (120 bits) are used. The rest are thrown away.

Notice that the sig (the signature) is part of what gets hashed. This has a surprising consequence. The signature algorithm used (ECDSA) is usually randomized. So, if you sign the exact same genesis operation twice, you (usually) get 2 different signatures — and thus 2 different DID-PLCs.

Self-Certifying

Because the code is a hash of the genesis operation, a DID-PLC is self-certifying.

Anyone can get the genesis operation from the directory, hash it, and check that the result matches the DID. The directory cannot make up a different genesis operation for a DID — because it would have a different hash.

And, because the genesis operation is signed by one of the keys listed inside of it, and every later operation is signed by a key from the operation before it, the whole log of operations can be checked. Nobody needs to trust the directory to tell the truth about who controls a DID.

Operations

A (regular) operation has the following fields:

type

always the string "plc_operation".

rotationKeys

an array of public-keys (as did:key strings). These are the keys that control the DID. Only these keys can sign the next operation. They are listed in order of descending authority — the first key has the most authority. (At least 1 key.)

verificationMethods

a map of names to public-keys (as did:key strings). For ATProto, the name is atproto, and the key is the account's signing-key.

alsoKnownAs

an array of URIs. For ATProto, this includes the handle, as an at:// URI.

services

a map of names to services, where each service has a type and an endpoint. For ATProto, the name is atproto_pds, the type is AtprotoPersonalDataServer, and the endpoint is the URL of the account's PDS.

prev

the CID (a type of hash) of the previous operation. For the genesis operation, it is null. (It must be there, with the value null. It cannot be left out.)

sig

the signature of the operation.

Note that the names in verificationMethods and services do not start with #. The # gets added when the DID document is made.

Also note that the operation is not the DID document. The directory turns the most recent operation into a DID document when someone asks for it. (And, the rotationKeys are not included in the DID document.)

There are 2 other types of operations: plc_tombstone and the legacy create. We will get to those later.

Rotation-Keys versus Signing-Key

A DID-PLC has 2 different kinds of keys. And, it is important to not confuse them:

rotation-keys

in rotationKeys. These control the DID itself. Whoever has the private-key for a rotation-key can change the handle, the PDS, the signing-key, and even the rotation-keys. They are only used to sign PLC operations.

signing-key

in verificationMethods (as atproto). This is used by the PDS to sign the account's data (its repository). It has no control over the DID (unless it is also listed as a rotation-key).

Best practice is to keep these separate — i.e., do not use the same key as both a rotation-key and a signing-key.

For a typical Bluesky account, the PDS holds both the signing-key and a rotation-key. A user can also add their own rotation-key (with more authority) so that they can recover their account without the PDS's help.

Handles and alsoKnownAs

The handle in alsoKnownAs is a claim. The directory does not check it. Anyone can create a DID-PLC that says at://atproto.com.

So, an ATProto app must verify a handle bi-directionally:

  1. the DID document must claim the handle (in alsoKnownAs), and
  2. the handle must point back to the DID — either with a DNS TXT record at _atproto.<handle> with the value did=<DID>, or with an HTTPS response from https://<handle>/.well-known/atproto-did whose body is the DID.

Only when both directions agree should the handle be trusted.

DAG-CBOR

Operations are sent to (and received from) the directory as JSON. But they are signed and hashed as DAG-CBOR.

Why‽ Because JSON can be written many different ways — with different spacing, with different key orders, etc. And, to hash or sign something, everyone must agree on the exact bytes.

CBOR (short for Concise Binary Object Representation, RFC-8949) is a binary format similar to JSON. DAG-CBOR is a strict subset of CBOR (from IPLD) where there is only one way to encode any value. The rules that matter for PLC operations are:

  • lengths are encoded using as few bytes as possible,
  • lengths are always given up-front (no “indefinite-length” items),
  • map keys are sorted — shorter keys first, and keys of the same length sorted byte-wise.

Every CBOR item starts with a head. The top 3 bits of the first byte are the major type. The bottom 5 bits are the length (if the length is less-than 24), or say how many more bytes hold the length (24 means 1 byte, 25 means 2 bytes, 26 means 4 bytes, 27 means 8 bytes).

Signing

To sign an operation:

  1. encode the operation as DAG-CBOR without the sig field (not with sig set to null — leave it out completely),
  2. hash those bytes with SHA-256,
  3. sign the hash with ECDSA, using the private-key of one of the rotation-keys, which gives you 2 numbers: r and s,
  4. make it “low-S” — if s is greater than half of the curve's order n, replace s with n - s,
  5. write r as 32 big-endian bytes, followed by s as 32 big-endian bytes (64 bytes total),
  6. encode those 64 bytes as base64url, with no = padding.

The result goes in the sig field.

Why “low-S”‽ Because for any valid ECDSA signature (r, s), the signature (r, n - s) is also valid. If both were allowed, someone could change the signature (and thus change the hash of the operation) without knowing the private-key. So, only the “low” one is allowed. The directory rejects “high-S” signatures.

Export

The set of all DID-PLCs, and all of their operations, is public. You can download all of it with /export.

/export returns JSON Lines (one JSON object per line). It takes 2 query parameters:

count

how many operations to return (at most 1000).

after

a cursor — the seq number of the last operation you got. Use after=0 to start from the beginning.

To get the next page, use the seq of the last line as the next after.

(If you leave out after, or use a timestamp for after, you get an older format, without seq, which is sorted by createdAt. Its use is discouraged.)

There is also a WebSocket at wss://plc.directory/export/stream that streams new operations as they are accepted. It takes an optional cursor (a seq number) to catch up from.

Adding a New DID-PLC

To add a new DID-PLC to plc.directory:

  1. create the keys — at least 1 rotation-key, and (for ATProto) a signing-key,
  2. create the (unsigned) genesis operation, with "prev": null,
  3. sign it with (the private-key of) one of its rotation-keys, and add the sig,
  4. calculate the DID-PLC from the signed genesis operation,
  5. POST the signed genesis operation, as JSON, to https://plc.directory/ followed by the DID.

That's it. There is no account to sign up for, and no API key. The directory checks that the signature is valid, and that the DID in the URL matches the hash of the operation. If both are correct, the DID is registered.

A few warnings:

  • Operations are permanent. Once a DID is added to plc.directory, it (and its whole history) is public forever. It can be deactivated (with a tombstone), but it cannot be removed. So, do not experiment against https://plc.directory.
  • Keep the rotation-key. If you lose the private-key of every rotation-key, you can never change the DID again. And, if someone else gets it, they can take control of the DID. (Printing it, like this example does, is only for learning. Store it somewhere safe.)
  • The handle and the PDS must be real for the DID to be a working ATProto account. Normally, a PDS creates the DID for you when you create an account on it. You would do this yourself if you are writing a PDS, or managing your own identity.

Updating

To change a DID-PLC (for example, to change its handle, or move it to a different PDS), you add a new operation to its log.

An update operation is just like a genesis operation, except:

  • it must contain all of the fields (not just the ones that changed),
  • prev is the CID of the previous operation (instead of null),
  • it must be signed by one of the rotation-keys of the previous operation,
  • it is POSTed to the URL of the existing DID.

To permanently deactivate a DID-PLC, you add a tombstone operation. It only has 3 fields:

It is signed (with a rotation-key) the same way as any other operation. After a tombstone, the directory returns a 404 (DID not available) for the DID document and data, and rejects any further operations. But the log (including the tombstone) is still there, and still public.

(A tombstone can still be undone during the 72-hour recovery window — see below.)

72-Hour Recovery Window

Remember that rotation-keys are listed in order of descending authority? This is why.

Let's say a DID has 2 rotation-keys: your own key (first, most authority), and your PDS's key (second). And, let's say your PDS gets hacked, and the attacker uses the PDS's key to submit an operation that removes your key.

For 72 hours after that operation, a key with more authority (a lower position in the rotationKeys of the operation before it) can “rewrite history”. It does this by submitting a new operation whose prev points to the last good operation (from before the attack). The directory then marks the attacker's operation(s) as nullified.

A key with the same or less authority cannot do this. (If you try, you get Invalid signature on op.) And, after 72 hours, nobody can.

Nullified operations are still in the audit log (with "nullified": true), but not in /:did/log.

Privacy

Everything in the log of a DID-PLC is public, and permanent. This includes every handle it ever had, every PDS it was ever on, and the time of every change (including when it was created). Even after a tombstone.

So, for example, if someone changes their handle from their real name to a pseudonym, the old handle is still there for anyone to see.

And, if 2 DIDs use the same rotation-key or signing-key, anyone can see that too.

Trust

plc.directory is a central server. But, because operations are signed, and DIDs are self-certifying, there is a limit to what it can do. It can not forge an operation. What it can do is:

  • refuse to accept or serve operations (denial of service), or
  • if there is a fork in the history, choose the “wrong” fork.

Because /export lets anyone download (and check) every operation, anyone can run a mirror of the directory, and audit it.

A Note on k256

The examples in this article use P-256 keys, because Go's standard library supports P-256. But, many ATProto keys are k256 (secp256k1) keys. For example, all the keys of did:plc:ewvi7nxzyoun6zhxrhs64oiz start with did:key:zQ3s. (The reference ATProto implementation generates k256 keys by default.)

To use k256 in Go, you would need a third-party package (such as github.com/decred/dcrd/dcrec/secp256k1/v4). Then, use the multicodec prefix 0xe7 0x01 instead of 0x80 0x24, and the k256 curve order for low-S. Everything else — DAG-CBOR, SHA-256, base32, the 24 characters — stays the same.

There are also complete Go implementations of DID-PLC, such as github.com/did-method-plc/go-didplc.

History

DID-PLC was created by Bluesky (Bluesky Social PBC) in 2022, while designing ATProto. They wanted a DID method that was strongly consistent, highly available, recoverable, and cryptographically secure, with fast and cheap updates — and were not satisfied with any of the existing DID methods.

The first operation in plc.directory is from 17 November 2022.

PLC originally stood for “Placeholder”. (The specification used to be titled “DID Placeholder Method”.) The name was meant to say that it was not intended to stay the same forever. In October 2024 the specification was changed to say that PLC stands for “Public Ledger of Credentials”.

In September 2025, Bluesky announced that it would create an independent organization to run the directory, as a Swiss association. And, in September 2026, the PLC Organization (plcred.org) announced that it formally existed, as a registered Swiss association, and that its next step is to get ready to take over the directory's assets and operations.

Summary

  • A DID-PLC is did:plc: followed by a 24 character code.
  • The code is the first 24 characters of base32(sha256(dagcbor(signedGenesisOperation))).
  • Operations are JSON on the wire, but are signed and hashed as DAG-CBOR.
  • Rotation-keys control the DID. The signing-key signs the account's data.
  • Get information with GET https://plc.directory/<did> (and /data, /log, /log/audit, /log/last).
  • Add a new DID (or update one) with POST https://plc.directory/<did>.
  • Everything is public and permanent — so experiment against a local directory.
